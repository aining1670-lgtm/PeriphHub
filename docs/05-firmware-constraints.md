# Incott G23 固件约束（协议事实，可复用）

设备：`093A:522C`（2.4G 接收器）/ `093A:622C`（Type-C 有线）。

## 1. 报文

- Feature Report 严格 **9 字节**：`[0x09, cmd, p1..p7]`；读命令 `cmd | 0x80`
- 响应首字节回显读命令（如 `0x89`）
- 传 65 字节缓冲区会导致驱动报错或返回垃圾
- 宏走 **Output Report**：`[0x09, ...32 字节]`，共 33 字节；
  必须 `WriteFile`（`HidD_SetOutputReport` 返回成功但固件忽略）
- 写入前校验 `featLen == 9 && outLen == 33`，不满足立即中止

## 2. 指令表

| Cmd | 作用 | 参数 |
|---|---|---|
| `0x8F` | 型号/握手 | 返回 `psd`、型号、`receiverType`、传感器；**没有固件版本字段** |
| `0x09/0x89` | 基础状态 | 电量 %、充电、回报率码；**当前 DPI 档不在这里**（见 `0x83`） |
| `0x02/0x82` | 单 DPI 档 | `[02, slot, hwLo, hwHi, R, G, B, axis]` axis 0=XY 1=X 2=Y；读回 `[82, slot, hwLo, hwHi, 0...]` |
| `0x03/0x83` | DPI 档表 | 写 `[03, 档数, 当前档]`；读回 payload[0]=档数、payload[1]=当前档（0 基） |
| `0x04/0x84` | 传感器 | sub 1=LOD 2=波纹 3=角度 4=MotionSync 5=模式 |
| `0x05/0x85` | 杂项 | sub 1=去抖 2=连发 3=休眠（LE16 秒，实测保留上限 900s，见 §10） |
| `0x06/0x86` | 按键绑定 | 低 6 键；index 9 = 板载配置序号 |
| `0x07` | 宏上传 | 10 轮：头 `[07,10,chunk,32,slot,0,0,0]` → 40ms → 32B Output |

## 3. 硬性限制

1. **宏回读不可靠**：G24 的 `0x87` 返回 `FF`（`adapter.js` 注释）；G23 待真机验证 → 不伪造回读，PC 端存（`macros.ini`，UTF-16）
2. **网页校验上限**：宏 `item` ≤ 71 项、`cycle` 1–65535、`delay` 0–65535、名称 ≤32；编码时最后一项 `bit0=0` 作停止标记，cycle 低/高字节都写入。旧版文档写的 70/255 与网页实现不符，P5 用真机复核固件实际行为
3. **连发**：`loops` 0–3、`interval` 0–255（`apply()` 内钳位）
4. **LOD 编码错位**：0=1.0mm / 1=2.0mm / 2=0.7mm（官方网页驱动自身有此 bug）
5. **8K 回报率**：仅 `receiverType==2` 且 2.4G；WP5 起普通接收器明确拒绝 >1000Hz（返回错误，不钳位）
6. **60 秒浅休眠**：握手可用、深层读取超时 → 提示「移动鼠标唤醒」
7. **双 Collection**：有线/部分接收器暴露两个 `UsagePage 0xFF05`，第一个拒绝 Feature，
   必须**倒序探测**
8. 宏槽号必须等于按键索引（官方 `apply()` 的隐性约束）
9. 从磁盘载入的宏不能标记为「已写入设备」：固件不可回读，Apply 必须重传

## 4. 网页 Studio 宏文件格式

```json
{
  "format": "incott-studio-macro",
  "version": 1,
  "macro": {
    "name": "封顶32字符",
    "looptype": 1,
    "cycle": 1,
    "uid": 1763740000000,
    "item": [ { "key": "KeyA", "press": true, "delay": 30 } ]
  }
}
```

- 文件名约定 `incott-macro.json`，UTF-8 无 BOM，导入上限 128 KB
- `key` 是浏览器 `KeyboardEvent.code`，共 108 个（keyboard HID page + `LButton/RButton/MButton` = `0xF0..0xF2`）
- `uid` 是 `Date.now()`，超过 32 位 → 导入时取低 32 位
- 键表来源：网页 `define-v100.js` 的 `vkPOS`；用 `tools/gen_golden.js` 生成 `golden/keys.json`。快照已存 `golden/define-v100.js`（脚本优先读 `build/define-v100.js`，缺失时用这份），离线也能重生成 `native/src/keytable.inc`

## 5. P1 真机证据（2026-11-21，G23 2.4G）

设备路径 `\\?\hid#vid_093a&pid_522c&mi_02&col02#...`（FeatureLen=9，OutLen=33）；同一 `mi_02` 下的 `col01` 是 FeatureLen=0、OutLen=33，必须跳过 → 证实倒序探测必要。

读写方式：`HidD_SetFeature` 发 `[09, cmd, 0...]` → 30ms → `HidD_GetFeature` 读回。

- 两个调用都要求缓冲区首字节是 report ID `0x09`；`HidD_GetFeature` 若首字节为 0 会直接返回 false（`GetLastError` 可能为空），这是 P1 实现时踩到的坑。
- `0x8F` → `09 8F 01 02 01 00 F0 00 00`
  - `[1]` psd=0x01；`[2]` model=0x02 → G23；`[3]` receiverType=0x01（1K，非 8K）；`[4]` 有线传感器位=0x00；`[5]` 无线传感器位=0xF0 → 3395
  - USB `bcdDevice=0x0000`，0x8F 没有固件字段；官方/第三方 UI 也没有固件版本显示
- `0x89` → `09 89 20 01 00 08 00 00 5A`
  - `[1]`=0x20=32，电量原始值；网页按 10% 向下取整
  - `[2]`=0x01（charging 状态，第三方把 2 当充电中）；`[3]`=0x00（1000Hz）；`[4]`=0x08（P2 复核后确认**不是**当前 DPI 档，见第 6 节）
  - `[6]` 两次读取在 01/00 间变化；`[7]`=0x5A=90，含义待复核
- `0x81`/`0x83` 首次读取返回全 0/空报告，疑似设备浅休眠；P1 只依赖 0x8F/0x89

## 6. P2 真机证据（2026-11-21 23:15，G23 2.4G，`--info`）

- `0x83` → `09 83 06 02 00 00 00 00 00`：`[2]`=6 档、`[3]`=2 当前档（0 基），与 `setDpiInfo` 写入布局一致（payload[0]=档数、payload[1]=当前档）
- 6 个档位实测 `[400, 800, 1600, 2400, 3200, 6400]`，与第三方 `adapter.js` 默认 `dvar.dpi` 完全一致
- `0x82 slot` → `09 82 slot hwLo hwHi ...`：`hw = [4]<<8 | [3]`、`dpi = (hw+1)*50`（slot 2 的 `1F`→1600，slot 5 的 `7F`→6400）
- `0x02` 写 `[09, 02, slot, lo, hi, 0, 0, 0, axis]`；X=Y 用 axis=0 单帧，X≠Y 先 axis=1、100ms 后 axis=2
- **写一次即落板载**：写 slot 2 = 2400 后拔插 2.4G 接收器，再读仍是 2400；不需要额外 `0x06/09` 提交
- **写后立即回读会拿到空报告**（`09 00 00 ...`），50ms 后重试即得真实回读（官方 `adapter.js` 同样重试 3 次），CLI 已内置 3 次
- `0x89` → `09 89 20 01 00 08 00 01 5A`：`[2]`=32 电量、`[3]`=1、`[4]`=0（1000Hz 码）、`[5]`=8、`[7]` 在 00/01 间变、`[8]`=0x5A；`[5]` 与 0x83 当前档（2）不符 → 当前档一律以 `0x83` 为准
- `0x85` sub3 → `09 85 03 3C ...` = 60s 休眠；sub1 → `09 85 01 08 ...` = 去抖 8ms

## 7. P4 真机证据（2026-11-21 23:54，G23 2.4G，`--keys` / `--set-key`）

帧内偏移按 9 字节 feature 报告绝对下标（`[0]`=report ID 0x09，`[1]`=cmd）。

- **读键 0x86**：发 `09 86 <matrix> 00 00 00 00 00 00`；回包 `09 86 <matrix> b0 b1 b2 b3 ...`，`code = b3<<24|b2<<16|b1<<8|b0`（LE32，等价第三方 `rdata[5]<<24|...|rdata[2]`）。`[2]` 必须回显请求的 matrix，否则视为坏帧（已按第三方 `readKEY` 校验）。
- **写键 0x06**：`09 06 <matrix> b0 b1 b2 b3 00 00`（LE32）。
- **0x06 不回显**：`Feature()` 读回的是上一份报告（实测拿到 `09 8F ...`），不能用写回包判断成败；必须靠 0x86 回读。
- **写后首次 0x86 必为全零**（`09 00 00 00 00 00 00 00 00`，固件异步应用），50ms 后重试即得真实值；CLI/桥均内置 3 次重试，见 `WriteKey()`。
- **6 键 matrix 顺序** `[0,1,2,4,3,5]`（左、右、滚轮、前侧、后侧、DPI）；第三方 `gvarG23-v100.js` 同序。
- 本机默认绑定实测：`0x00F00001` 左 / `0x00F10001` 右 / `0x00F20001` 中 / `0x00F40001` 前侧(m4) / `0x00F30001` 后侧(m3)；**DPI 键（m5）读回 `0x00050009` = 宏槽 5**，说明当前板载配置把它绑成了宏，具体内容待 P5 复核（第三方默认是 `0x00030007` DPI 循环）。
- 键码编码（第三方 `keyinfo_to_hw`，已逐值对拍）：鼠标 `0x00F00001/0x00F10001/0x00F20001/0x00F40001(前)/0x00F30001(后)`；DPI `0x00030007` 循环、`0x00010007` +、`0x00020007` -；配置切换 `0x0000F10A`；连发 `0x0218F00A`；键盘无修饰 `usage<<8|0x80`、带修饰 `usage<<16|(mod<<8)`（mod 低 4 位 Ctrl=1/Shift=2/Alt=4/Win=8）；媒体 `usage<<16|0x0003`；宏 `slot<<16|0x0009`（槽号=按键索引）；关闭 `0`。
- 键名表 108 项来自网页 `define-v100.js` 的 `vkPOS`，用 `tools/gen_golden.js` 生成 `golden/keys.json` + `native/src/keytable.inc`（脚本必须匹配逐行 `vkPOS[i++]=[...]` 形式，旧的数组字面量正则无效）。
- **静置休眠**：设备闲置后 0x86/0x83/0x85/0x82 **全部**返回全零，只有 0x8F/0x89 仍应答；物理移动鼠标后立刻恢复。CLI/网页应提示「移动鼠标唤醒」，不要把全零当真实读数。**WP5 验收补充（2026-11-22）**：浅休眠下 `0x01` 写与 `0x81` 读**仍被应答**且回真实 rate 码（见 §10）——`0x81` 不能当探活命令，rate.* 须先读 `0x83` 探活。
- 持久化：`--set-key 4 KeyA` 后拔插 2.4G 接收器再读仍是 `0x00000480`，按键仍打出 `a` → 与 DPI 一样写一次即落板载。

帧内偏移按 9 字节 feature 报告的绝对下标（`[0]`=report ID 0x09，`[1]`=cmd）。

## 8. P5 真机证据（2026-11-22 00:12，G23 2.4G，`--macro-apply` / `macros.upload`）

**上传通道（实测可用）**：每块先 `Feature(09 07 0A <chunk> 20 <button> 00 00 00)`，`Sleep(40)`，再 `Output(09 + 32B payload)`；10 块后写 `0x06`。固件不回显 `0x07`，不校验块序，但块间 <20ms 会丢块（40ms 稳定）。宏内容 320B 布局见第 4 节，用 `protocol::EncodeMacro` 生成。
**缓冲号 = 按键 index**：`buffer 4` 上传后 `0x06` 写 `(4<<16)|0x0009`，`--keys` 读回 `0x00040009 Macro:4`；`buffer` 与库槽位无关（槽 6 的宏上传到 buffer 4 也是 `Macro:4`）。
**悬空按下会被丢弃**：3 项宏 A↓ A↑ B↓，真机只打出 `a`；补一条 B↑ 后打出 `ab`。因此保存/导入时自动补末项松开，71 项已满则拒绝（`last action is a press; the 71-action limit leaves no room for its release`）。
**回读延迟**：写 `0x06` 后首次 `0x86` 常为全零，实测最长 ~300ms；`WriteKey` 用 60ms + 5×100ms 重试后稳定，宏绑定不再假 MISMATCH。
**持久性**：宏内容在固件（`setMacro` 即写板载），拔插接收器、断电后仍在；PC 侧只需要保存「库槽 ↔ 按键」的映射（`macros.ini` 的 `bind` 行）与宏本体。
**不可回读**：`0x87` 读宏仅 G24 固件实测可用，G23 返回全零，所以库是唯一副本。
**71 项 + 65535 循环**：71 项（末项松开）、`cycle=65535` 保存/上传均成功；`cycle=65536` 与 72 项在打开设备前即被拒绝。
**本机默认宏槽**：后侧键出厂绑 `fmsBACK`，DPI 键在本机板载配置里是 `0x00050009 Macro:5`（读回，未解）；P4 验收后已恢复后侧键为 `Mouse:Back`。
**本地库**：`macros.ini` UTF-16LE + BOM，首行 `periphhub-macros 1`；沙箱下 `%LOCALAPPDATA%` 写入会被 ACL 拒绝（Win32 error 5），验收用 `PERIPHHUB_DATA_DIR` 指到仓库内目录。

## 9. WP2 真机证据（2026-11-22 18:15，G23 2.4G，`--bridge` misc/keys）

- **连发参数 0x05 02**：写 `[09, 05, 02, loops, interval]`，读 `0x85 02` 回包 `[09, 85, 02, loops, interval, ...]`（bytes[3]=loops、bytes[4]=interval，与第三方 `readResponse(0x85,2)` 的 `data[2]/data[3]` 对应）。`misc.set {fireLoops:2,fireInterval:50}` → 回读 `{fireLoops:2,fireInterval:50}`，`misc.get` 复读一致。本机出厂值 `3/10`（与第三方预设默认一致），验收后恢复。
- **越界拒绝**：`fireLoops:5` / `fireInterval:300` 均返回 `ok:false`（严格拒绝，不钳位）。
- **Fire 码**：`keys.set index=4 binding="Fire"` → 写 `0x0218F00A`，`0x86` 回读一致；随后两次 `keys.get` 均报 `binding:"Fire", kind:"fire"`。连发目标固定为鼠标左键（固件 Fire 码只连点左键，官方参数只有 loops/interval 两个）。
- **keys.set 不收 Macro:N**：`binding:"Macro:3"` → `ok:false`（"Macro:N is set via macros.upload…"），防「按键指向从未上传过的缓冲」。
- **静置休眠坑**：0x06 写入后 0x86 六次回读全零 → `readback mismatch: wrote 0x0218F00A got 0xFFFFFFFF`，原因是设备再次浅休眠（0x8F/0x89 仍应答）；唤醒后同一条命令立即成功。休眠期 `0x85 sub2` 读不到 → `misc.get` 的 fireLoops/fireInterval 返回 `null`（不伪造默认值；**WP5 已修复**：debounce/sleep 读失败/回显不匹配同样回 `null`，四个字段口径一致，不再回退 8/60）。
- **出厂绑定基线（本次实测）**：`[Mouse:Left, Mouse:Right, Mouse:Middle, Mouse:Forward, Mouse:Back, Dpi:Cycle]`；DPI 键为 `0x00030007`（P4 时的 `Macro:5` 已被官方驱动/重置改回第三方默认）。

## 10. WP5 真机证据（2026-11-22，G23 2.4G，0x84 sub5 / 0x85 sub3 对拍）

**传感器模式（0x84 sub5）在 1000Hz 下不锁 0**：官方数据模型注释 `this.sensormode = 1; //默认标准模式（0=节能模式，1=标准模式，2=竞技模式）`（`.research/official-js/public-v101.js:30`）。基线读 `09 84 05 01 00 00 00 00 00` → modeRaw=1。逐值试写（帧 `[09, 04, 05, v, 00, 00, 00, 00, 00]`，与桥 `sensor.set` 的 `MakeWrite(kCmdSensor,[sub,val])` 帧完全一致）：

| 试写值 | 回读 | 结果 |
|---|---|---|
| 1 | `09 84 05 01 …` =1 | 基线本就 1，验证写读通道 |
| 2 | `09 84 05 02 …` =2（写后首次读为旧值/空报告，60ms 重试取到） | 固件保留 |
| 1 | `09 84 05 01 …` =1 | 恢复成功 |
| 0 | `09 84 05 00 00 00 01 00` =0 | 官方 <2000Hz 的锁定值，固件同样保留 |
| 1 | `09 84 05 01 00 00 01 00` =1 | 再恢复 ✓ |

- 结论：**固件不锁模式**，0/1/2 写入均被保留并精确回读（1↔2、1↔0 双向验证）。「官方在 usbrate<2000 把模式锁 0」只是官方 UI 的前端行为；第三方 studio 在 rate≥2000 自动写 mode 2 也是同一原因（`.research/third-js/studio.js` 的 `key === "rate" && value >= 2000` 分支）。
- UI 呈现：PeriphHub 自由提供 0/1/2 三档并按真实回读显示；数据层面不做 <2000Hz 锁定，仅在 ≤1000Hz 时提示该官方行为差异。旧 UI 的 0=竞技/1=普通/2=办公 与官方数据模型矛盾，「办公」无官方依据，WP5 起按官方语义显示。
- LOD 线上编码照官方保留：0=1.0mm / 1=2.0mm / 2=0.7mm（§3.4 的官方错位），不「修正」。

**休眠上限实测（0x85 sub3，LE16 秒，任意值语义而非预设表）**：`misc.set {"sleep":N}` 后原始读回：

| requested | readback | accepted | 说明 |
|---|---|---|---|
| 900 | 900 | 是 | `09 85 03 84 03 00 00 01 00` = 900s 精确保留；随后恢复 60 回读 `09 85 03 3C 00 …` ✓ |
| 1000 | 60 | 否 | 桥当时报 `ok:true` 但回读 = 写前旧值 60s。设备醒着（WAKE_OK、回读 tries=1、0x83 b7 在 01/00 活动跳变）→ 固件拒绝；非截断（若按 LE16 低字节截断应为 232s） |
| 1800 | 60 | 否 | 拒绝而非截断（截断应为 8s） |
| 950 | 60 | 否 | 排除「<1000 全收」的简单上限 |
| 850 | 850 | 是 | `09 85 03 52 03 …` 保留 → 任意值语义；上限落在 [900,949] |
| 300 | 300 | 是 | `09 85 03 2C 01 …` 保留 |
| 60 | 60 | 是 | 基线值；每次恢复后回读 `09 85 03 3C …`，共 7 次恢复全部成功 |

- 结论：固件接受任意秒数直至某上限；**实测可用最大 900s**（900 收、950 拒），拒绝不是截断也不是钳位（回读一律保持旧值）。精确上限在 900–949 之间，949 待测。官方 `DormancyTime` 预设最大也是 900 秒，`misc.set` 的 sleep 上限按 900 实施（`protocol::kSleepSecondsMax`）。
- 桥层缺口（WP5 修复）：修复前 `misc.set` 对 sleep 只写不回读（固件拒绝 950/1000/1800 时桥仍报 `ok:true`），`sensor.set` 忽略 `device.Feature` 返回值且写后不回读（静默失败时 UI 显示旧值）。WP5 起逐参数/逐 sub 回读比对（0x84/0x85 回包 `bytes[2]` 必须回显请求的 sub），失败 `ok:false`。

**浅休眠下 0x01/0x81 仍被应答（WP5 真机验收补充，2026-11-22）**：75s 零 HID 流量后的干净睡态轮（睡态由同轮相邻 get 证实：`sensor.set {"lod":0}` / `misc.set {"debounce":8}` 正确 `ok:false`，`sensor.get`/`misc.get` 全 `null`）里 `rate.set {"hz":1000}` → `ok:true` 且回读 code 0、`rate.get` → code 0。结论：浅休眠时 `0x01` 写与 `0x81` 读**仍被接收器应答并返回真实 rate 码**（rate 是接收器侧状态），而同轮 `0x83/0x84/0x85` 深读全为空报告/无回显——`0x81` 自身无法识别睡态。修复：`rate.get`/`rate.set` 先读 `0x83` 探活（无回显或 count<1 = 睡着，见 §7）；睡着时 `rate.get` 回 `{"code":null,"hz":null}`（同 misc.get/sensor.get 形状）、`rate.set` 返回 `device sleeping (move the mouse to wake it)` 且不写 `0x01`。第二轮复测因用户在用鼠标已醒，不作睡态证据；睡态测试写入值均与基线相同，无状态漂移。

**探活修复的复测状态（2026-11-22）**：修复后两次重测（75s / 100s 零 HID 流量静置）设备均因用户持续使用**未入睡**，六条桥命令全回真实值（`rate.set {"hz":1000}` → `ok:true data code 0`、`sensor.get`/`misc.get` 全真实值）——这两轮**硬件验证了探活的醒态路径**（rate.* 能回真实值 ⇔ `DeviceAwake` 判醒正确，未误判睡态）与醒态语义未破坏；**睡态路径的真机复测仍未完成**（自然入睡不可复现：设备睡态与用户活动相关，0x89[7]=0x5A 指向 ~90s 阈值但活跃后不触发），待设备可静置 ≥2 分钟时单独补测。睡态判据本身的真机依据：docs/05 §7 P4 实测「静置休眠后 0x86/0x83/0x85/0x82 全零、仅 0x8F/0x89 应答」+ 验收第 1 轮同窗口 0x84/0x85 全 null。

## 11. WP3 真机证据（2026-11-22，G23 2.4G，0x82 形状对拍）

**0x82 每档只有一个值：[3..4] 存「最后一帧 0x02 写入的值」，与帧内 axis 字节无关**。读回布局 `09 82 slot hwLo hwHi ...`，`hw = [4]<<8|[3]`、`dpi=(hw+1)*50`。顺序实验（均先写后等 100ms/读回）：

| 实验 | 回包 | 读数 | 说明 |
|---|---|---|---|
| slot2 基线 | `09 82 02 1F 00 00 00 00 00` | 1600 | 基线（X=Y） |
| X=800 → Y=1600（axis=1 → 100ms → axis=2） | `09 82 02 1F 00 00 00 00 00` | 1600 | = 最后写入的 Y |
| X=1600 → Y=800（axis=1 → 100ms → axis=2） | `09 82 02 0F 00 00 00 00 00` | 800 | = 最后写入的 Y |
| Y=800 → X=1600（axis=1 最后写） | `09 82 02 1F 00 00 00 00 00` | 1600 | = 最后写入的 X → 排除「[3..4] 固定存 Y 寄存器」 |

- **axis-aware 读无效**：读请求 payload 带 axis=1 / axis=2（`[09,82,02,0,0,0,0,0,1]` / `[…,2]`）的回包与 axis=0 逐字节相同 → 固件忽略读请求的 axis 字节，无法按轴读。
- **X≠Y 写序后 X 读不到**：官方/第三方 X≠Y 写序固定 axis=1(X) 先、axis=2(Y) 后（`MakeDpiWrite` 同序），因此 0x82 读回恒为最后写的 Y。桥层结论（WP3 实施）：`dpi.get`/`dpi.set` 按「单值 = 最后写入轴（官方写序下 Y；X=Y 档即真值）」呈现，`x`/`dpiX` 恒 `null` 并带 `unverified` 标注，不把单值同时当作 X 展示。
- **写后立即回读仍可能拿空报告**（同 §6），50ms 间隔重试即可；实验组与基线回包 [5..8] 均为 `00 00 00 00`。
- **0x03→0x83 档位切换与同步已实测通过（2026-11-22 / 2026-11-23）**：`dpi.stage` 按 4×50ms 重试防御写后短暂旧表窗口，3/6、5/6 往返及还原 2/6 真机通过，UI `setDpiCount`/`selectDpiStage` 切换并同步 `0x82` 真实读回已确认通过；0x03 仅存 `count/active`，档位变更后重读 `0x82` 即可拿到真实 Y 值。

**0x02 写帧 RGB 字节（[5..7]）是否覆盖板载灯色：字节层面无法证实，本轮标记「未验证」，不改码**。证据：所有 0x82 回包 [5..7] 全程 `00 00 00`（slot2 基线 `09 82 02 1F 00 00 00 00 00`、XY 写后 `09 82 02 1F 00 00 00 00 00`、交换写后 `09 82 02 0F 00 00 00 00 00`、反序补测恢复后 `09 82 02 1F 00 00 00 00 00`；6 个 slot 基线读的 [5..7] 也全 00），而桥/官方规定的写帧 RGB 字节本就是 `00`——「写前后不变」既证明不了「回包不含 RGB」，也证明不了「本机 slot RGB 本来就是 000000」。未做非零 RGB 写探针：若读回不含 RGB，写 `FF0000` 会真实改掉板载灯色且无法从回包恢复原色，对用户在用设备风险不可接受。旁证（仅推断，非字节证据）：官方 setDPI 帧同样恒带 RGB=00 且用户灯色日常存在 → 若该写真覆盖灯色，官方每次调 DPI 都会关灯——倾向 preserved，但不据此改判。落点：PeriphHub 写帧保持 RGB=00，UI 色板降级为纯「界面标识色」（本地 UI 元数据，仅前端展示，不宣称板载灯色/板载已同步）。
